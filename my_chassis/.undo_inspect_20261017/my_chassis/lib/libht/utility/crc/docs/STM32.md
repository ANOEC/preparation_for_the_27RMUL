# STM32 硬件后端

`adapters/stm32/` 提供基于 STM32 CRC 外设的可选后端。它默认不启用，也默认不被注册。

结论先说：在 STM32H723（550 MHz）上实测，**这个后端比软件查表慢 1.5 到 4 倍**，因此本工程编译它但不注册它。它的价值在于为低端芯片和 flash 紧张的场景保留选项，以及已经验证过与软件结果完全一致。

## 启用条件

源文件自带门控，在非 STM32 环境下编译为空目标文件，因此可以无条件加入任何构建而不会破坏它。判定分两步，只依赖 ST 的 CMSIS 头文件自己提供的宏：

1. `__has_include()` 查找 CMSIS 系列头文件（`stm32h7xx.h`、`stm32g4xx.h` 等）。找不到就不包含，不会因为缺少头文件而编译失败。这一步必须用 `__has_include`，因为无法先包含头文件再判断是否身处 STM32 环境。
2. 用 CMSIS 定义的寄存器宏决定可用性，要求同时存在 `CRC_BASE`、`CRC_CR_RESET`、`CRC_CR_POLYSIZE`、`CRC_CR_REV_IN_0`、`CRC_CR_REV_OUT`，以及一个已知的 CRC 时钟使能位。

第 2 步顺带排除了 STM32F1/F2/F4：这些系列的 CRC 外设是固定多项式（CRC-32/MPEG-2），没有 `POL`、`INIT` 和反射配置，本后端在上面无法工作。它们会自动退回软件路径，而不是编译失败或给出错误结果。

时钟使能位按系列选择：

| 宏 | 寄存器 | 典型系列 |
|---|---|---|
| `RCC_AHB4ENR_CRCEN` | `RCC->AHB4ENR` | H7 |
| `RCC_AHB1ENR_CRCEN` | `RCC->AHB1ENR` | G4、L4、L5、U5、WB |
| `RCC_AHBENR_CRCEN` | `RCC->AHBENR` | F0、F3、G0、L0、C0 |

三个宏都不存在时后端不可用。

### 供调用方判断的宏

头文件总会定义 `CRC_STM32_BACKEND_AVAILABLE` 为 `1` 或 `0`。为 `0` 时不声明任何接口，所以调用处需要自己判断：

```cpp
#include "crc_stm32.hpp"

#if CRC_STM32_BACKEND_AVAILABLE
  crc::stm32::Init();
  crc::InstallBackend(&crc::stm32::HardwareBackend());
#endif
```

定义 `CRC_STM32_BACKEND_DISABLE` 可以在具备条件的环境里强制关闭。

### CMake

库导出两个变量，由使用方自行加入，因为 CMSIS 头文件的搜索路径只有使用方才有：

```cmake
target_sources(your_firmware PRIVATE ${CRC_STM32_ADAPTER_SOURCES})
target_include_directories(your_firmware PRIVATE ${CRC_STM32_ADAPTER_DIR})
```

本工程在根 `CMakeLists.txt` 里这样接入；主机测试构建不加这两行，即使加了也只会得到空目标文件。

## 实现

外设没有结果异或级，`XorOut` 在软件里完成。每次计算：

1. 写 `POL`、`INIT`。
2. 写 `CR`：按宽度设置 `POLYSIZE`，按 `refin` 设置 `REV_IN` 为按字节反转，按 `refout` 设置 `REV_OUT`。
3. 置 `CR.RESET` 把寄存器载入初值。
4. 以 8 位宽度逐字节写 `DR`。
5. 读 `DR`，按宽度截断，异或 `XorOut`。

逐字节写入而非按字写入，是为了实现简单并天然处理任意长度。代价见下一节。

`supports` 接受宽度为 8、16、32 的任意参数组合，因为 `POLYSIZE`、`REV_IN`、`REV_OUT` 都可编程。

## 实测数据

STM32H723VGTx，内核 550 MHz，AHB 275 MHz（`AHBCLKDivider = RCC_HCLK_DIV2`），DWT 周期计数，`-O0` 调试构建。

正确性：四个预设 × 长度 0 到 309 字节，共 1240 组比对，硬件与软件结果全部一致。

耗时拟合为线性模型：

| 路径 | 每字节周期 | 固定开销 |
|---|---:|---:|
| 硬件（四个预设均相同） | 12.0 | 83 |
| 软件 `Crc8MaximReferee` | 5.0 | 10 |
| 软件 `Crc16Mcrf4xx` / `Crc32IsoHdlc` | 8.0 | 12 |

309 字节的实测原始值（周期，软件 / 硬件）：

| 预设 | 5 B | 18 B | 127 B | 273 B | 309 B |
|---|---|---|---|---|---|
| `Crc8MaximReferee` | 35 / 143 | 96 / 299 | 641 / 1607 | 1371 / 3359 | 1551 / 3791 |
| `Crc16Mcrf4xx` | 52 / 145 | 152 / 298 | 1024 / 1606 | 2192 / 3358 | 2480 / 3790 |
| `Crc16Ibm3740` | 60 / 142 | 131 / 299 | 894 / 1607 | 1916 / 3359 | 2168 / 3791 |
| `Crc32IsoHdlc` | 60 / 143 | 151 / 298 | 1023 / 1606 | 2191 / 3358 | 2479 / 3790 |

## 为什么硬件更慢

瓶颈不是 CRC 计算，而是把数据喂给外设。

内核 550 MHz，CRC 外设挂在 275 MHz 的 AHB4 上。每写一个字节都是一次跨总线矩阵和 AHB4 桥的外设访问；外设区是 Device 内存，强序、无法深度流水，实测单次约 6 个 AHB 周期，折合 12 个内核周期。同时 Cortex-M7 这边的软件查表几乎免费：表常驻 D-cache，取表加异或移位，双发射流水线还能重叠，只要 5 到 8 个周期。

最直接的证据是上表里硬件那一列：CRC8、CRC16、CRC32，反射与非反射，耗时完全相同（309 字节都是 3790 左右）。算法复杂度对硬件毫无影响，因为 CRC 单元本身一个 AHB 周期算完一字节，时间全部花在总线传输上。软件那边则随宽度变化（5 对 8 个周期），因为移位和掩码的工作量不同。

还要注意硬件的**每字节斜率本身**就比软件差，不是固定开销拖累。所以任何长度下硬件都不会反超，不存在交叉点。

这个结果符合架构预期。外设是为低端芯片设计的：在 48 MHz 的 M0/M0+ 上，总线与内核同频、没有 cache，软件查表可能需要 15 到 25 个周期一字节，这时硬件明显占优。

## 可能的优化

`DR` 是 32 位寄存器，一次可以写 4 个字节。改成按字写入可以把总线事务数减少到约四分之一，每字节摊到约 3.3 个周期，反而会比软件快一倍。

反射类算法把 `REV_IN` 设为 `0b11`（整字 32 位反转）配合小端字读取即可，效果与现在逐字节 `REV_IN=0b01` 完全等价：小端载入的字反转全部 32 位后，外设按 MSB 优先依次处理 `rev(b0)`、`rev(b1)`、`rev(b2)`、`rev(b3)`，与逐字节反射喂入的序列相同。非反射的 `Crc16Ibm3740` 需要先 `__REV` 一次，一条指令的代价。

没有实施的原因是不值得：最大 309 字节的帧软件也只需 4.5 µs。对比之下，裁判系统 115200 波特率收一个 127 字节帧本身就要 11 ms，RMLink 的泵周期是 1 ms。CRC 不是瓶颈，而按字写入需要处理首尾不对齐的字节，会在一段校验相关的代码里增加分支。

## 板上自检

```cpp
#if CRC_STM32_BACKEND_AVAILABLE
  crc::stm32::Init();
  const auto result = crc::stm32::RunSelfTest();  // 检查 result.mismatches == 0
#endif
```

`RunSelfTest()` 直接驱动外设、绕过库内的互斥标志，因此**只能在 `Init()` 之后、`InstallBackend()` 之前运行**，且期间不能有其他代码使用该外设。它对四个预设和 0 到 309 字节数据比对软硬件结果，并以 DWT 周期计数测量 `kSelfTestSizes` 各长度的耗时。首次调用会在必要时启用 DWT 计数器。

本工程验证时的做法是在 `app_main` 里临时调用它，把 `SelfTestResult` 存入一个全局变量，再用调试器读回该变量的地址。移植到新芯片时建议先跑一遍：不同系列的 `REV_OUT` 在 8 位和 16 位多项式下的行为值得实测确认。
